# Skill: Unit Tests — FIRST Principles

## Purpose

This skill defines the **FIRST** principles that every unit test generated by the Unit Test Generator agent must satisfy. Apply these criteria when writing tests and include a FIRST compliance checklist in `test-report.md`.

---

## The FIRST Principles

### F — Fast
- Tests must complete in milliseconds, not seconds.
- No real network calls, database connections, or file I/O.
- Use mocks/stubs for external dependencies.
- A full suite should finish in under 10 seconds.

**Checklist item**: _Does each test complete without I/O or network?_

---

### I — Independent
- Tests must not depend on each other's state or execution order.
- Each test sets up its own preconditions and cleans up after itself.
- No shared mutable state between test cases.

**Checklist item**: _Can each test run alone and in any order?_

---

### R — Repeatable
- Tests must produce the same result on every run regardless of environment, time, or external state.
- Avoid `Date.now()`, `Math.random()`, or environment-specific paths without mocking.
- CI and local runs must yield identical results.

**Checklist item**: _Does the test always return the same pass/fail?_

---

### S — Self-Validating
- Tests must use assertions (e.g., `expect`, `assert`) — no manual inspection of console output.
- Outcome must be a clear boolean: **pass** or **fail**.
- The test runner should be the sole judge.

**Checklist item**: _Does the test assert outcomes automatically?_

---

### T — Timely
- Tests should be written at the same time as, or immediately after, the production code they cover.
- Tests for bug fixes must cover the exact scenario that caused the bug.
- Tests should not be written months after the fact from memory.

**Checklist item**: _Do tests target the exact change made by the Bug Implementer?_

## Test Quality Rules

1. One logical assertion per test (multiple `expect` calls are fine when testing the same logical outcome).
2. Descriptive test names: `should return 404 when user ID does not exist`.
3. Arrange → Act → Assert (AAA) structure.
4. Cover: happy path, edge cases, and error paths.
5. Only test the **changed or new code** identified in `fix-summary.md`.
